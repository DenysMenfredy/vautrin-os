# V0.4 platform admin setup and operations

The platform console is a separate internal application. Local development
uses `http://localhost:8081`; the customer app stays on
`http://localhost:8080`, and both call the Nest API on port 1447. Admin
authorization is disabled until an operator explicitly bootstraps the first
SUPER_ADMIN.

## Local setup

1. Keep the current `.env` private. Set `NODE_ENV=development`,
   `POSTGRES_PLATFORM_PASSWORD` to a local-only password, and configure:

   ```dotenv
   DATABASE_PLATFORM_URL=postgresql://vautrin_platform_admin:URL_ENCODED_PASSWORD@localhost:5435/vautrin?schema=public
   ADMIN_BASE_URL=http://localhost:8081
   APPLICATION_BASE_URL=http://localhost:8080
   ```

   The password embedded in `DATABASE_PLATFORM_URL` must match
   `POSTGRES_PLATFORM_PASSWORD`. URL-encode special characters. `.env.example`
   values are published local-development placeholders and are not secrets.

2. Start local Postgres/Redis and prepare the restricted platform database role
   and schema:

   ```sh
   pnpm infra:up
   pnpm --filter @vautrin/api setup:admin
   ```

   The setup command requires matching loopback URLs for `DATABASE_URL`
   (`vautrin_app`), `DATABASE_MIGRATION_URL` (`vautrin_migrator`), and
   `DATABASE_PLATFORM_URL` (`vautrin_platform_admin`). It refuses production
   mode, remote databases, mismatched databases, or the wrong roles. It grants
   no platform access and does not restart applications.

3. Build the workspace, then run API and customer web as usual and start the
   admin app in another terminal:

   ```sh
   pnpm build
   pnpm --filter @vautrin/admin dev
   ```

   If running the full Docker Compose stack, use `pnpm docker:up`; its startup
   migration handles the schema and the init script creates the restricted
   local role. Rebuild/recreate containers after changing environment values.

## Grant the first console access

The admin app intentionally has no default account or password. First create
an invitation for an owner using the existing trusted tenant-onboarding flow,
deliver its one-time 43-character token privately, and have the invitee accept
it with their own password. The accepted identity must be active and already
have a password before it can receive platform access. This preserves the
existing identity and invitation rules; admin operations never set a customer
password.

When you are ready to assign the first platform operator, run this once from a
trusted local shell with the restricted platform database URL configured:

```sh
pnpm --filter @vautrin/api bootstrap:admin --email EXISTING_ACCEPTED_USER_EMAIL
```

The command grants SUPER_ADMIN to that existing identity and writes an audit
event. It refuses if an active SUPER_ADMIN already exists and never creates a
user or issues an invitation. The initial SUPER_ADMIN remains unassigned until
you deliberately run this command. After the first grant, manage platform
access inside the authenticated console. The last active SUPER_ADMIN cannot
be suspended, downgraded, disabled, or deleted.

## Invitation behavior

Tenant creation may optionally issue the initial OWNER invitation through the
same service used by the tenant API. Existing identities are reused; their
current password is not changed. New invitees set their password during the
existing acceptance route. Tokens are random 256-bit base64url secrets,
persisted only as SHA-256 hashes, expire after seven days, and are returned
once. The console can copy the invitation URL for private delivery; it does
not send email. Reissuing explicitly revokes the prior pending token.

## Production preparation

1. Provision a unique `vautrin_platform_admin` PostgreSQL login with
   `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOINHERIT`. Use
   `infra/scripts/bootstrap-db.sql` through the approved private DBA path,
   supply `VAUTRIN_PLATFORM_PASSWORD` through the environment, and run the
   application migrations as the migration identity. The API alone receives
   `DATABASE_PLATFORM_URL`; worker and customer web do not.
2. Set API `ADMIN_BASE_URL=https://ADMIN_DOMAIN` and
   `APPLICATION_BASE_URL=https://CUSTOMER_DOMAIN`. Use separate HTTPS origins.
   Create a private `environment.tfvars` with `admin_domain`; DNS must point
   that hostname to the existing load balancer. Plan/review Terraform before
   any apply. Terraform apply is not run by the admin frontend workflow.
3. Configure the protected GitHub `staging` environment with
   `ADMIN_FRONTEND_BUCKET`, `ADMIN_ORIGIN`, and `APPLICATION_ORIGIN`, plus the
   GCP workload identity variables required by the deployment workflow. The
   admin static release is built and promoted independently with
   `infra/scripts/deploy-admin.sh`; the workflow smoke-checks its routes,
   headers, API routing and origin policy.
4. Run `bootstrap:admin` only from a trusted private operator environment
   after the intended owner has accepted an invitation. Do not place the
   platform URL/password in frontend build variables or a browser bundle.

## Lifecycle and recovery

User deletion is logical: it disables authentication, revokes tenant/admin
sessions, revokes memberships and pending invitations, suspends platform
access, and preserves the user and audit history. Tenant archive revokes
active-tenant sessions and pending invitations; tenant/customer data is not
purged. Every state-changing platform action is audited in the append-only
platform log. Do not edit or remove audit rows to correct an action; perform a
new authorized state change with a reason.

If there are no active SUPER_ADMIN accounts, use the trusted bootstrap command
with an existing active, invitation-accepted identity. It is intentionally
one-time and will refuse when an active SUPER_ADMIN already exists. If one
still exists but cannot log in, restore access through that identity or follow
the reviewed private DBA incident procedure; do not create a hidden default
account.

## Local troubleshooting

- **Platform administration is not configured:** verify
  `DATABASE_PLATFORM_URL` is set only for API/CLI, points to the restricted
  role, and matches local database name/port.
- **Untrusted request origin:** admin login/logout and mutations require the
  exact `ADMIN_BASE_URL` Origin. Open the console on port 8081 and ensure both
  configured origins match the browser URLs.
- **Login rejected:** verify an active SUPER_ADMIN exists and that the user
  has accepted an invitation and set their own password. Tenant OWNER alone
  does not provide platform access.
- **Session remains stale after a change:** admin sessions are checked live;
  sign in again after access or role changes. Customer JWTs are also rejected
  when the user, membership, or tenant has been disabled/revoked/suspended.
