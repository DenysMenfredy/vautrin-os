# Run the v0.3 revenue path locally

The API, worker, PostgreSQL and Redis must all run. The frontend alone cannot
execute automation. Full voice intake is deferred: Settings provides an
authenticated, idempotent missed-call adapter for controlled testing.

## Build and migrate

Use the pinned Node/pnpm versions (`nvm use`, `corepack enable`). Keep your existing
`.env` and database. Run `pnpm install --frozen-lockfile`, `pnpm build`, then
`pnpm db:deploy` against the intended local database before restarting the apps.
The new migration adds agent execution identity and leases; it does not seed or
change existing customers. Start infrastructure with `pnpm infra:up`, then API,
worker and web with their `pnpm --filter @vautrin/... dev` scripts.

Sign in with an existing tenant owner. New tenants use the existing
`onboard:tenant` / invitation acceptance flow; provider credentials are separate
from the owner's login. The existing sample seed remains opt-in.

## Provider configuration

In `.env`, set `OPENAI_API_KEY` from your OpenAI project. Only the worker needs it.
Choose an explicit model available to that project when installing the template.
No real model or paid provider requests run in the deterministic test suite.

For host development, set `LOCAL_SECRET_DIRECTORY` to an absolute private
folder, for example `/home/YOUR_USER/projects/vautrin-os/.local-secrets`, and set
`LOCAL_SECRET_ENCRYPTION_KEY` to the output of `openssl rand -hex 32`.
API/operator commands write AES-GCM encrypted credentials there; worker reads the
same directory/key. Do not commit `.env`, the key, or the secret folder. Local
storage is rejected when `NODE_ENV=production`; GCP uses attached identities and
Secret Manager instead. Keep the key: losing it requires reconnecting providers.

For root Docker Compose, use `NODE_ENV=development`, create `.local-secrets` with
mode 0700 and ownership writable by container UID 1000 before starting. Compose
mounts it at `/var/lib/vautrin/secrets`, writable in API and read-only in worker.
If provisioning from the host, its `LOCAL_SECRET_DIRECTORY` must refer to that
same host folder. `LOCAL_SECRET_HOST_DIRECTORY` can override the bind path.

### Twilio messaging

Provision a dedicated test sender, Messaging Service and API key in Twilio.
Load a private JSON file outside the checkout into an approved environment name:

```sh
export VAUTRIN_TWILIO_LOCAL="$(cat /PRIVATE/PATH/twilio.json)"
pnpm --filter @vautrin/api configure:twilio --tenant-id TENANT_UUID \
  --phone-number +1YOUR_SENDER --public-api-origin https://YOUR_TUNNEL_HOST \
  --credentials-env VAUTRIN_TWILIO_LOCAL
unset VAUTRIN_TWILIO_LOCAL
```

The JSON requires `accountSid`, `apiKeySid`, `apiKeySecret`, `webhookAuthToken`
(the account Auth Token used to verify signatures) and `messagingServiceSid`.
Set the Messaging Service incoming webhook to the returned URL. Set its status
callback URL to the same origin and `/api/webhooks/twilio/status/INTEGRATION_UUID`.
Use a controlled recipient allowed by your Twilio test/account setup. The tunnel
must preserve the configured external webhook URL for signature validation.

### Google Calendar

Create a Google OAuth Web application with Calendar API enabled, configured
consent screen/test user and redirect URI matching `.env`. Set
`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` and
`GOOGLE_OAUTH_REDIRECT_URI=http://localhost:3002/api/integrations/google-calendar/callback`.
Restart API, then connect from Settings using a calendar you can edit. Consent
uses PKCE, an expiring one-time state and an HttpOnly browser nonce. Refresh
credentials are encrypted and each connection pins an immutable credential version; API list responses contain safe configuration only.
In production the redirect must use HTTPS and the application origin.

## Install and exercise

1. In Settings, install the remodeling template with your actual postal coverage,
   timezone and OpenAI model. Installation adds five service entries, six lead
   fields, qualification rules, a consultation booking type, receptionist and
   two workflows. Existing nonempty business configuration is preserved; review
   it before testing. Reinstallation returns the same template identities;
   subsequent changes use the versioned workflow/agent editors.
2. Configure providers. Record a controlled missed call in Settings. The default
   recovery waits 30 seconds; the reconciler polls every five seconds. Follow-ups
   default to two hours and one day, and stop on reply, handoff, opt-out or changed
   lead state. A retry of the same submission uses the same intake identity.
3. Reply to the SMS. Give service, property type, postal code, budget, timeline
   and project description. Qualification decisions come from application rules.
4. Explicitly select an offered time (first/second/third, or its full ISO time).
   Booking rechecks qualification, hours, notice, horizon and provider conflicts.
   A model cannot confirm a booking without a successful booking tool.
5. Inspect Automation activity on Overview, run details, usage and the human inbox.
   Cancelling a run stops future work; an external action already in flight may
   finish and requires operator review. STOP suppresses further outbound SMS.

Provider failure retries have persisted attempt counts/due times and bounded
backoff. Exhaustion produces a failed workflow and human handoff. External tool
claims prevent blind duplicate side effects after uncertain outcomes.

## Isolated verification

`infra/docker-compose.test.yml` supplies PostgreSQL on 5545 and Redis on 6380.
Use its synthetic test credentials and export `NODE_ENV=test`, database URLs,
`REDIS_URL`, `EMBEDDING_DIMENSIONS=1536` and a disposable `JWT_SECRET`. Apply
migrations, then run `pnpm test:integration` and `pnpm test:e2e`. Never point these
suites at a customer database or shared Redis. Unit/component tests use `pnpm test`.
Versioned receptionist cases are in `packages/e2e/evals/receptionist-v1.json`.
Real model behavior and provider/GCP drills remain separate release evidence.
