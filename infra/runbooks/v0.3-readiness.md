# V0.3 release drills

Use an isolated staging project and controlled synthetic customer identity.
Record commands/results and restoration/rollback times with the release SHA.
This document describes drills; it is not evidence that a live drill passed.

## Backup and restore

Confirm Cloud SQL automated backups and seven-day PITR are enabled. Take a
backup before each risky migration (`gcloud sql backups create --instance=SOURCE`).
Clone into an isolated staging recovery instance with
`gcloud sql instances clone SOURCE RECOVERY --point-in-time=RFC3339_TIME`.
Never restore over the active customer database during a drill. Connect privately
and verify schema/migration history, sampled synthetic lead/message/appointment
state, audit history, runtime role flags, FORCE RLS and cross-tenant denials.
Run the deterministic release gate against a separate disposable test database.
Record restore duration, recoverable timestamp and observed data loss. Delete the
temporary recovery instance only after its results have been reviewed.

## Redis loss and workflow recovery

In staging, pause the worker and capture IDs/due times for an unpublished event,
a scheduled wait and a scheduled agent action. Remove ONLY the dedicated staging
queue data through an approved operator action. Restart the worker. Confirm the
outbox/reconciler reconstruct the jobs, waits respect PostgreSQL due times,
cancelled workflows remain cancelled and one provider mutation occurs for each
stable identity. Exercise unknown SMS acceptance outcomes: never blindly resend;
use signed status callbacks and flag an unresolved send for an operator.

## Deployment rollback

Deploy a known revision, run topology/auth/provider smoke, then deploy a compatible
new revision. Promote the previous revision with `PROMOTE_ONLY=1 DEPLOY_SHA=SHA`
and the deployment script. Verify API/worker guest revision attributes, readiness,
static asset/deep routes and session rotation. Check that Redis/durable database
state survive. Record any outage. Do not reverse additive migrations during an
application rollback; use a reviewed compensating migration if necessary.

## Provider staging smoke

Provision a dedicated Twilio sender/subaccount and Google test calendar. Verify
sender registration and permission to contact the controlled test identity.
Record a missed call, observe recovery SMS, submit a reply, collect qualification
facts, explicitly select an offered slot and check the real calendar event. Confirm
STOP suppression, human handoff, audit, run history and token usage. Revoke a
calendar grant and confirm safe failure/handoff. Real model evaluation is additional
release evidence: deterministic tests verify policy enforcement, not model quality.

## Evidence checklist

Record: revision; project; date; operator; backup/PITR config; restore result/time;
rollback result/time; same-origin static/API/cookies; effective proxy/IP config;
runtime RLS; Redis TLS and recovery; provider test identity/results; model/prompt
version and behavior eval; alert delivery; known limitations and release approval.
